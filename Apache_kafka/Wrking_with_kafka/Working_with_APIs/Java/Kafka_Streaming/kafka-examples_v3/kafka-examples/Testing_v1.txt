Notes**
how a KStream-KTable left join behaves in Kafka Streams:
When using TopologyTestDriver, if no record has ever been written to the KTable topic before the stream record arrives, the left 
join produces no output at all — not even a null-profile record.

In a real running cluster, the left join would emit with a null right-side. But TopologyTestDriver 
processes records synchronously and the KTable state store is completely empty for CUST-999, so Kafka Streams silently drops it rather
than emitting with null.

So in Test: To match the real behaviour — assert the output IS empty for an unknown customer in the test driver, 
and a comment that explains the real-cluster behaviour.

Remember: TopologyTestDriver is synchronous and strict — it only joins what's already in the store at the exact moment the record arrives. 
A real Kafka cluster has eventual consistency and buffering, so the left join null-fallback path in OrderEnrichmentPipeline does fire in production.

Important Note**
__consumer_offsets > is Kafka's internal topic where all consumer group offsets are stored. 
When your Java app calls commitSync(), it writes to this topic. When your app restarts and calls subscribe(), 
it reads from this topic to know where to resume.
This is why LAG=0 persists even after your app stops — the committed offsets are durable, 
stored in Kafka itself, not in your app's memory.

DLT with the failure reason attached. In production an ops team would monitor this topic and fix + replay those records.

3. Producer and consumer ran concurrently — notice the interleaving in the logs. Batch 1 and 2 were being produced 
while the consumer was already processing. Batch 3 arrived while the consumer was mid-way through batch 2.

U-003 count=2 appears 3 times — same 2 clicks visible across 3 different overlapping windows
That's the hopping behaviour — one event counted in multiple windows simultaneously
This is why hopping is used for "rolling last 30s" stats updated every 10s

SESSION gap=15s — activity-based variable windows:
U-003 — 2 pages viewed, session started at 04:30:20 — closed after 15s inactivity
U-002 — 1 page viewed in their own separate session
Window size was variable — determined by activity, not a fixed clock

The suppress() effect — notice tumbling windows only emitted once per window with the final count, not an intermediate update for every click. 
Without suppress() you'd see a count of 1, then 2, then 3 as each click arrived. With it you only see the final 3 when the window closes.
